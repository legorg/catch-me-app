# Catch me! game specification

Status legend: **[done]** implemented, **[next]** planned in the given milestone, **[planned]** agreed, rules still open.

## Principles

- **No human gamemaster.** The backend is the referee. The person who creates a game picks the playground and then joins like every other player, with no extra rights.
- **Objective rules only.** Every rule must be decidable by the server from stored data: positions, timestamps, and player actions.
- **Server-enforced visibility.** Clients only receive what the requesting player may see. Hidden data never leaves the backend; the UI does not merely hide it.
- **Lazy time evaluation.** There is no game loop. Time-based transitions (countdown finished, reveal due, time limit reached) are derived from stored timestamps whenever a request touches the game. This survives restarts and needs no scheduler.
- **Friendly play.** GPS spoofing cannot be fully prevented; the rules aim to be fair among honest players and robust against normal GPS error.

## Roles

| Team / role | Goal |
|---|---|
| Runners | Reach the route's stop landmark without being caught. |
| Hunters | Catch runners before they reach the route's stop landmark. Final team scoring is still open (see Finish and end). |
| Spectators ("Zuschauer") [joining, lobby and map done; timeline planned] | Watch all available player locations without taking part in gameplay; event timeline planned. |

### Spectators [backend/UI done; timeline planned]

- **Direct joining [backend/app implemented]:** a separate six-digit **spectator code** joins through the existing `POST /api/players` with `{code, name}` and returns a normal authenticated player token. The start screen explains all three invitation types; the code decides the affiliation, not a separate client-side role choice. Creators can also choose "Join as spectator" after creating a game. Only the lobby/countdown permits joining; at the scheduled start or after game end, joining returns `409`. Spectators count toward the **30-participant limit** and shared case-insensitive name uniqueness, but not readiness/end conditions. Joining/leaving a spectator before start does not reset/cancel the countdown. No ready-up or switch into a playing team is allowed. Leaving is still only supported before start. Spectators have no administrative powers.
- **Direct spectator identity/API [implemented]:** `team: spectator` records original non-playing affiliation, while `role: spectator` controls viewing. Converted runners retain `team: runner` and their terminal outcome. Direct spectators have no runner row/outcome, hunter team, position history, team sketches or joker uses. Their state has its own team-discriminated variant: common game/player metadata, the shared runner `route` and `jokers: []`, with no route-regeneration counter or sketches. Before start it exposes no player locations; while running it exposes the same latest-real-report feed as converted runners. Results include direct spectators as `{playerId, name, team: spectator}` and list them in a separate spectator section without fabricated runner/hunter data. Converted runners remain in the runner result section with their outcomes.
- **Spectator lobby [app implemented]:** show participant names and a separate spectator roster without ready/not-ready indicators. Explain that location access and ready-up are unnecessary, joining/leaving does not alter the countdown, and player locations appear only after start. Hide permission cards, own GPS dot/locate button (inline and fullscreen), route/team controls and the Ready button. Keep the pre-start Leave action. Do not start foreground/background tracking or send position reports; also stop a leftover background task on a restored spectator session. Action/permission handlers independently reject spectator requests. At countdown expiry open the same spectator game map; normal restore and ended-game result navigation apply unchanged.
- **Automatic transition [backend implemented]:** an accepted catch or finish immediately makes that runner a spectator. The authenticated game state adds `role: player | spectator`, independent of original affiliation (`team: runner | hunter | spectator`). For converted runners the role derives from the persisted terminal runner state, without a second stored flag. Preserve original affiliation, outcome and timestamps for end-condition evaluation, statistics and history. No client-supplied role or switch back to active participation is supported.
- **Map:** spectators see the latest available real positions of **all runners and all hunter teams**, without periodic-reveal delays or joker-based concealment. Fake positions must not replace real spectator positions. Caught/finished runners no longer report locations: show only their last stored catch/finish location and status, not a purported live location. Finish coordinates remain hidden from active hunters, even though spectators may see them.
- **Location feed [backend implemented]:** unrestricted player locations are supplied **only while status is `running`**, never in the lobby/countdown or after game end. Spectator responses use each player's `position` for the latest real report, including a finished runner's frozen last report, identified by `runner.status: finished` and the report's `recordedAt`. Caught runners retain `runner.caughtPosition` instead of `position`; no report is invented if none exists or retention has removed it. Spectators receive no periodic `reveals`. Active-player projections stay restricted. This is only latest-report access, not full position history. Spectators also receive the same start/destination landmarks as runners, including before start; this does not grant sketches, other players' joker histories or a timeline. All-state responses include the viewer's role, while keeping the existing team-discriminated response variants.
- **Spectator map [app implemented]:** the existing game screen switches on the server's `role: spectator`, including on a restored session. Draw only the real player-report feed while running: **blue runners**, **red hunters** from every hunter team, frozen **black ×** catches, and **blue ✓** last reports of finished runners (including oneself). Pin titles identify name/team/outcome; descriptions show report timestamps/accuracy, hunter-team names where present, and explicitly label finished reports as frozen with no further tracking. Catch descriptions include catch and last-report times. No report means no player marker, never a historical/fake fallback. Direct spectators and converted runners see the same start/destination pins as runners, both in the lobby and on the game map; the game info also names the landmarks and route distance. Route updates before start are reflected by polling. Hide reveal/joker snapshots, zone overlays, sketches and compass lines. The HUD shows the spectator role, own caught/finished outcome where applicable and the color/symbol legend, without a reveal countdown or own out-of-bounds warning. Info explains latest-report semantics, missing/expired reports, tracking stop and fair play. No catch/finish/joker/drawing controls, own GPS dot, locate button or permission prompts. Even an already-open joker screen shows no spectator gameplay actions. Confirmed spectator permission cannot be undone by stale responses. Existing game-end navigation opens results. Timeline and replay remain planned.
- **Event timeline [backend/API and spectator app implemented]:** `GET /api/me/timeline`, polled by spectators, returns `{serverTime, events}`. The timeline is derived from the stored game state (start/end time, runner outcomes, joker uses); there is no separate event table that could drift from it. Events, discriminated by `kind`: `gameStarted` (only once the scheduled start is reached), `hunterJokerUsed` (`hunterTeam`, `joker`), `runnerJokerUsed` (`runner: {playerId, name}`, `joker`), `trapTriggered` (`hunterTeam`, without the runner), `zoneAlert` (`runner`, `hunter`, `hunterTeam`, without the cell), `runnerCaught` and `runnerFinished` (`runner`), and `gameEnded`, each with `at`, oldest first, only up to the server's current time. Each event kind has exactly its own required fields. Events carry no coordinates, cells or joker results. Only viewers with `role: spectator` receive it; active runners/hunters are rejected (`409`). **App:** spectators get a timeline button in the game screen's action bar; it opens a card over the map (closing the info card) that lists the events newest first with local clock time and a text per event. It polls every 5 seconds only while open and the screen is focused; older responses never replace newer ones, and errors appear as a pill. **After the game end** everyone with the full game ID sees the whole timeline (oldest first) as `events` in the public result and as a "Timeline" card on the result screen. Planned target: show a chronological, game-wide timeline with server timestamps, including **which team used which joker and when**, the acting player where applicable, catches, finishes, players leaving, game start/end, and automatic joker events such as zone alerts and trap activation/triggering. Personal jokers identify their runner; hunter jokers identify the specific hunter team. Timeline and map access are enforced by the backend; active runners/hunters must not receive the unrestricted spectator feed.
- Spectators are **read-only**: no joker use, catching, finishing, route regeneration, or team sketches/actions. They do not report their own location, need no gameplay location permission, do not ready up, and do not count toward the start condition or the set of active runners. Converted runners stop foreground/background tracking and retain an authenticated session for watching.
- The live spectator map/timeline is separate from the **post-game result/history endpoint**, which remains accessible only after the game ends. Spectator access during a running game does not grant a pre-game-end full position-history/replay endpoint. On game end, spectators also automatically open the result view.
- **Still open:** timeline retention/event details and any future visibility of sketches or trap markers. Spectators see the runner route but no sketches or trap overlays. Spectators must not pass hidden information to active players (fair-play rule). There is no role-switch endpoint; rejoining with a second identity is not prevented by the current account-free development authentication.

## Playground [done]

- Square grid of 3 × 3 to 12 × 12 cells, chosen when creating the game, default 6 × 6, north-aligned unless rotated (below). Columns A, B, … (west to east), rows 1, 2, … (north to south), e.g. A1 to L12 for 12 × 12; on a rotated grid these directions turn with it.
- **Rotation [implemented; app not device-tested]:** the grid can be turned clockwise around its center by `rotationDegrees` (0–359 whole degrees, required when creating, 0 = north-aligned), fixed after creation. Row 1 and the last row turn with the grid: the route stop stays in row 1 ("northern edge row") and the start in the last row ("southern edge row"), whatever their compass direction. The server assigns positions to cells in the rotated grid (start/finish checks, zone jokers, trap, fake position). `playground.bounds` is the grid before rotation; clients turn it by `rotationDegrees` around `playground.center`. The landmark lookup searches the north-aligned rectangle around a cell and keeps only landmarks the grid assigns to that cell. **App:** the create screen has a "Grid rotation" card below the map with a slider from 0° to 355° in 5° steps (default 0°); the preview grid, its cell labels, the edge-row highlights of a chosen route and the map section follow while dragging. Route points left outside their edge row by a rotation are flagged like after moving the grid. All maps draw the rotated grid (labels stay upright), and the app assigns positions to rotated cells like the server.
- Cell side 100–5000 m in 100 m steps, default 2000 m.
- Center latitude within ±80°, no date-line crossing.
- The **reveal interval** (see Visibility) is chosen when creating the game: 1–60 whole minutes, default 30.
- **Joker allowances [implemented; app not device-tested]:** when creating the game, choose an allowance of **0–5 uses for each joker kind** (inclusive; 0 disables it), default 1. The create screen has a "Jokers" card with one 0–5 choice per kind, grouped into hunter jokers (per hunter team) and runner jokers (shared by all runners; fake position per runner). See Jokers for ownership details.

## Joining [done: milestone 1]

- Creating a game returns three distinct **join codes**: runners, hunters and spectators. Codes are 6 digits (`000000` to `999999`, leading zeros count); collision checks span all three affiliations across all games. Creation and lobby screens display all three as selectable text, with a separate native Share action per code. A shared invitation includes only that code, its affiliation and pre-start joining instructions, never the game ID, other codes or player credentials. Sharing errors leave copyable text available; cancellation is not treated as failure.
- A player joins with a code and a **display name** (1–20 characters after trimming, no control characters, unique per game ignoring case). The code decides the team.
- Joining returns a secret **player token**. Every later request authenticates with `Authorization: Bearer <token>`. The server stores only a SHA-256 hash of the token.
- At most **30 players** per game.
- Joining is possible in the lobby and during the countdown, not after the game has started.
- In the lobby, authenticated state includes all participants (names, affiliations, hunter teams, ready state) and all available join codes, so anyone (including the creator after joining) can invite participants. The spectator code is an invitation for live viewing after start, distinct from the confidential full game ID used for post-game results.
- **Development schema:** every game requires all three invitation codes, including a non-null, unique `games.spectator_code` and a required `joinCodes.spectator` API field. There is no compatibility path, nullable fallback or backfill for games from the earlier two-code schema; this is pre-production development. An incompatible local database may need an explicitly authorized reset; never automatically delete/reset it.

## Hunter teams [done]

- Runners are always one team. Hunters can form several **hunter teams**; all hunters share the same hunter join code.
- A hunter joins without a team. In the lobby and during the countdown, a hunter who is not ready **chooses a hunter team by name**: an existing team with that name (ignoring case, keeping its spelling) is joined, otherwise a new one is created. Names follow the display name rules (1–20 characters).
- A hunter team exists exactly while at least one hunter belongs to it; a team left by its last member disappears. There is no separate team record.
- A hunter can only get ready with a hunter team, so every hunter team has a player and every hunter has a team when the game starts. The development override does not skip this.
- Hunters win together (all hunter teams).

## Lobby and start [done: milestone 1]

- Each player toggles **Ready**.
- **Background location [app only]:** in installed builds, the app enables Ready only once "Always" location access is granted, so positions keep coming while the screen is off during the game. The server cannot verify the permission and does not check it; it can also be withdrawn later. Expo Go cannot share in the background, so there the app only requires foreground location access.
- **Start condition:** every player is ready, and each team has at least one player (hunters: see hunter teams).
- **Spectator exception [backend implemented]:** only runners and hunters participate in ready-up and start/countdown checks. Spectators neither satisfy a required team nor block/cancel the countdown by joining or leaving. Both `ready: true` and `ready: false` are rejected for spectators. A spectator-only game cannot start.
- When the start condition becomes true, the server schedules the start **10 seconds** later (countdown).
- Whenever the start condition stops holding during the countdown (someone joins, leaves, un-readies, or a ready runner leaves the start), the countdown is cancelled. It restarts from 10 seconds once the condition holds again.
- Once the countdown has passed, the game is **running**. Joining, leaving, and changing ready state are then rejected.
- Players can leave during the lobby and the countdown.
- **Leaving while running [planned]:** players can also leave an active game. A runner who leaves no longer counts as active for the end condition below. Closing the app or losing connectivity alone does not count as leaving. The rules above describe the current implementation until this is added.

Game status values: `lobby`, `countdown`, `running` (and `ended` from milestone 4).

## Route [done]

- Each game has **one route** that all runners share: a **start** in the southern edge row (the last row) and a **stop** in the northern edge row (row 1). The game creator picks one of two modes when creating the game:
  - **Generated [done]:** a start landmark in a random cell of the southern edge row and a stop landmark in a random cell of the northern edge row. The server picks both from a landmark lookup when the game is created; creating fails if an edge has no landmark.
  - **Chosen on the map [implemented; not device-tested]:** the creator places the start and the stop as plain points (no title, no landmark lookup). The server rejects (`400`) a start outside the southern edge row or a stop outside the northern edge row of the playground. A chosen route is fixed: it cannot be regenerated (`routeRegenerationsLeft` is 0, regenerating is refused with `409`). **App:** the create screen has a "Start und Ziel" card with "Automatisch" (default) / "Auf Karte wählen". The latter shows a map of the current grid with the southern edge row highlighted blue and the northern one red; a tap in the southern row sets the start, in the northern row the stop (pins), a tap elsewhere shows a hint. Points stay where they were tapped; if moving/resizing the grid leaves one outside its row, it is flagged and creating is blocked until it is set again. Untitled points are shown as "Start"/"Ziel". In the lobby the regenerate button is disabled with "no changes left", as for an exhausted generated route (the state does not tell the two apart).
- **Any runner** can **regenerate** a generated route, **2 times per game** in total (shared by all runners). Only in the lobby (not during the countdown or once running) and only while **no runner is ready**.
- Regenerating looks up the start and the stop again, each avoiding the current landmark. An edge without another landmark keeps its current one; if neither edge has another landmark, regenerating is refused and the count stays.
- Hunters have no start point. **Runners and spectators see the route**; hunters never see it. Spectators have read-only access, without regeneration or start/finish actions.
- **Display [app]:** start and destination are shown as two pins of one color of their own (cyan `#00bcd4`, used by no other marker) in the lobby, the game, the replay and while choosing a route; their names in the lobby/info texts use the same color. Their cells are not highlighted; only while choosing a route on the create screen are the southern (blue) and northern (red) edge rows highlighted.

## Start position [done: milestone 3]

- A runner can only get **ready** when their latest position lies within **50 m** of the route's start landmark and is at most **30 seconds** old.
- Before the start, a ready runner who reports a position farther away becomes **not ready** automatically (which cancels a running countdown).
- Once running, runners move freely.

Development testing only: `TEST_SKIP_START_POSITION_CHECK=true` (server flag `-test-skip-start-position-check=true`) temporarily bypasses this Ready/countdown position gate. Real position reporting is unchanged. The override defaults to off, applies to the development server rather than a stored game rule, and is exposed as `startPositionCheckDisabled` with a test banner in the app. Never use it for real games.

**Extension for finishing [done]:** the same environment variable and server flag also bypass the finish position gate; there is no separate finish-test switch. Despite its start-specific name, the override covers both start and finish checks. The existing `startPositionCheckDisabled` field remains the server's override indicator. The app shows a visible banner naming both disabled checks in the lobby and on the game screen. The override must never simulate, freeze, or replace GPS reports; real location tracking and reporting stay active until the runner actually finishes or otherwise leaves active play. It does not bypass authentication, role, game-phase, or active-runner checks, nor finish a runner automatically. It remains development-only, off by default, and unpersisted.

## Positions and visibility [done: milestone 3]

- Before the start, location is shared in the foreground only, while the lobby screen is open. Everyone shares from joining: runners for the start position check, hunters so their hunter team sees them.
- **Background sharing [done]:** while the game runs, players who grant "Always" location access keep reporting with the screen off or another app open (Android shows a notification while sharing). It stops when the player leaves the game screen, closes the app, or the token becomes invalid; a restarted app does not resume it. It needs an installed app build; in Expo Go and browsers the app falls back to foreground sharing.
- The app sends the latest fix every **5 seconds**, even when standing still. The server stamps each report with its own time and never trusts the phone's clock.
- Every reported position is stored as its own record; the newest is the player's current position. A player's positions are deleted when they leave.
- **Position history [stored; read only by the result]:** all records together are kept for a replay or chart after the game. Only the post-game result reads them (see "Game result and history view"), only after the game ended. Positions are deleted with their whole game (see Retention under "Game result and history view").
- Active players always see **their own** position. A caught runner instead gets the frozen catch location described below.
- **Hunters of the same hunter team** see each other's latest position **at any time**, including the lobby. Hunters never see other hunter teams' positions.
- **Runners** see each other's latest position **only while running**.
- **Hunters** receive each runner's position once every **reveal interval** after the start (the game's setting, 1–60 minutes, default 30; first reveal one interval after the start). A reveal shows where the runner was at the reveal time (their last report before it), not live updates. The state includes `nextRevealAt` and `revealIntervalMinutes` for both teams. Hunters get **every** reveal so far, oldest first (`reveals` per runner), not just the latest; the app fades older ones.
- **Runners** never see hunters, except the snapshot of the show hunters joker (see Jokers).
- Players outside the playground get a warning only; there is no penalty.
- Reveals are not stored: each reveal is derived from the stored positions as the runner's last report strictly before that reveal time. A reveal time before the runner's first report has no reveal.
- **Caught runners [done]:** everyone immediately receives `runner.status: caught`, `runner.endedAt` and, if a report exists, `runner.caughtPosition` (the last real report before declaring the catch). Their normal live position and all periodic reveals are omitted, including for themselves. Further reports are rejected. The catch location uses the existing position history and is deleted with the whole game (see Retention). New hunter location jokers exclude caught runners. Earlier joker snapshots remain historical results; the app suppresses their normal position markers for caught runners when drawing the catch marker.
- **Finished runners [done]:** after an accepted finish, the server rejects further reports and joker use. Everyone receives `runner.status: finished` and `runner.endedAt`, but no live position, catch position, or periodic reveals for that runner. New hunter location/zone/compass jokers exclude finished runners; reconstructed historical snapshots use eligibility and reports at the time of use and are not updated to the finish position. No finish-position marker is exposed. Stored reports stay subject to normal retention. Hunters never receive the route's stop landmark. Future traps/notifications must respect this restriction too, and post-game tracks may only be exposed once the whole game ends. The app stops foreground/background sharing for inactive runners, hides gameplay controls and obsolete normal markers, and rejects late responses that undo/change an outcome. Finished runners see a finished/watching status and no location-sharing prompts. The game info lists finished players by name for everyone, without coordinates or a finish marker.
- **Spectator visibility [backend/app implemented]:** team-restricted viewing rules above apply to active players. Authenticated spectators instead receive all available latest real player locations only while running, including frozen reports of retired runners. Direct spectators and converted runners use the same spectator map; neither sees player positions in the pre-start lobby. Broader spectator access does not broaden active-player responses. Event timeline remains planned; see Spectators.

## Catch, finish and automatic end [done: milestone 4; full history later]

- **Catch [implemented]:** while running, a runner can permanently mark **themselves** caught, on trust alone. No hunter proximity, position freshness, or reported position is required. The server timestamps the catch. Repeated requests succeed without changing the original catch time or location. Hunters and players in the lobby/countdown cannot declare a catch (`409`). There is no undo.
- A caught runner is **out**: no more position reports or joker uses (`409`), and no available jokers. Their token remains valid; the backend automatically grants `role: spectator` with all-location visibility while running, displayed on the app's spectator map. The event timeline remains planned. Existing position history is preserved for the later replay and normal retention.
- **App [implemented]:** active runners have an "I was caught" button with an irreversible-action confirmation explaining that the last reported location becomes public. Once a catch is confirmed, foreground/background reporting stops, the device location dot and locate control are hidden, and the runner's ordinary markers are replaced with a black × "Caught" marker at `runner.caughtPosition`, including on their own map. Everyone sees it on the next state poll, not waiting for a reveal. Without a report (or after retention), only the caught status is shown in the info panel's caught-player list. The caught runner sees the spectator HUD/map instead of location-sharing prompts and cannot open/use jokers. Late responses cannot roll back a confirmed catch or spectator permission; restoring an already-caught session also stops background sharing.
- **Automatic end [implemented]:** the last active runner's catch or finish changes the game to `ended` in the same database transaction and records the server time as the game's `endedAt`. The authenticated game state exposes this status/end time to every player; it has no `nextRevealAt` after the end. Further position reports (including hunters'), jokers, sketches, readiness/team/route changes, joining, and leaving are rejected. Retrying an already accepted catch/finish still succeeds, preserving both the runner's outcome/time and the game's end time; changing outcomes stays forbidden. The app stops foreground/background sharing for all players and opens the result route when it receives `ended`, including in an open joker modal or when restoring a completed session. An elapsed countdown never overrides `ended`; late responses cannot undo it. Position history and its retention are unchanged. No winner or time limit is implemented.
- **Finish [implemented]:** `POST /api/me/finish` permanently finishes the authenticated active runner while running. The backend checks the latest stored report using the **same position-check mechanism as runner Ready**, against the stop landmark: within **50 m**, at most **30 seconds** old. It uses server-recorded report timestamps and server time, not client coordinates or time. Missing, older-than-30-seconds, or farther-than-50-m reports cause `409`; the runner stays active. The server records the finished status and common end time, exposed as `runner.status: finished` and `runner.endedAt`. Repeated requests succeed without changing the original finish time or requiring another position check. Hunters, caught runners, and players before the running phase receive `409`; finished runners cannot later declare themselves caught. **App:** a **"Ziel erreicht"** flag icon appears beside the other HUD icons only while eligible, with an irreversible-action confirmation explaining the tracking stop, loss of joker access, destination privacy, and continued play for others. Eligibility uses the latest server-confirmed report, server time plus elapsed time since receipt, and the same 50 m / 30 s limits; expiry is reflected between polls. The request sends only the token, no coordinates or timestamp, and the backend rechecks. Entering the radius alone never finishes a runner. Catch and finish share one pending-request lock, disabling both icons during either request; failures remain visible and retryable. No local finished status or tracking stop is fabricated on failure.
- **Finish test override [done]:** `TEST_SKIP_START_POSITION_CHECK=true` (or `-test-skip-start-position-check=true`) bypasses the finish location requirement, including missing/stale reports, just like Ready. Normal authentication, role, game-phase, and active-runner checks remain enforced. No report is fabricated, and no runner finishes automatically. Real GPS tracking/reporting is unchanged until acceptance; further reports are then rejected and the app stops tracking when it receives the finished status. The app offers the finish icon regardless of location under this override and displays the banner naming both checks. This is only for stationary development tests, never real games or production.
- **After finishing [backend retirement/spectator transition and UI done]:** finishing is permanent; no further position reports or gameplay/joker use are allowed. The token remains valid for authenticated spectator access to all latest real reports while running, just like catching. Original runner affiliation and finish outcome remain unchanged. The spectator map displays frozen finish reports with a blue ✓; active hunters still receive no finish coordinates or destination.
- **End condition [implemented for caught/finished]:** the game ends automatically when **every runner has either been caught or finished**. The first finish alone does **not** end the game while another runner is still active; hunters do not count toward this condition, and empty/hunter-only games do not end automatically. The server stores `endedAt` permanently and derives status `ended` from it. All further gameplay location reports are rejected; the app stops sharing and navigates to the result once it learns of the end. Stored positions remain subject to normal retention. **Future extension:** count runners who left too, once leaving a running game is implemented; no `left` outcome is added yet.
- **Scoring and time limit [open]:** define the winner/statistics for mixed outcomes (finished, caught, left). The former "first finisher immediately wins and ends the game" rule is superseded. The previously proposed **90-minute** time limit is not implemented; whether it remains as an additional end condition, and how unfinished runners are scored then, must be settled before implementation.

## Next steps

Agreed topics whose rules are still open. Each needs its rules settled here before it is implemented.

### Backend model, database and API refactoring [done, before spectator roles]

- Separate shared player identity/participation from role-specific gameplay state before adding spectator transitions. Preserve the original runner/hunter affiliation and runner outcome independently of the current viewing role; becoming a spectator must not lose results or change which runners count toward the end condition.
- **Implemented internal model:** shared identity, authentication, readiness, and participation stay in `Player` / `playerRow`. A separate `RunnerState` value holds exactly one status (`active`, `caught`, `finished`) and a common `endedAt` (absent while active, required for either outcome). State fields are private and parsed on load. One shared transition mechanism permits only `active` -> terminal; same-outcome retries preserve the original timestamp, while changing or undoing an outcome is rejected. Add `left` only with the actual running-game leave feature. Original team affiliation is unchanged. There are no separate Runner/Hunter types throughout every layer.
- **Implemented persistence:** each runner has a one-to-one row in `runners` (`player_id`, `status`, `ended_at`); hunters have none. Foreign keys, uniqueness, and a status/time check constraint protect stored state. Position history remains shared. Runtime rules, eligibility for historical jokers, and visibility use this single runner state rather than competing timestamps.
- **No legacy data migration:** nothing is live, so this refactoring targets fresh development databases. There is no backfill or compatibility path for the former `players.caught_at` / `finished_at` columns. AutoMigrate creates the new schema but does not transfer old runner data or remove old columns. Existing games without `runners` rows are incompatible. Do not automatically delete or reset local databases; any reset requires explicit authorization. Once production data exists, use reviewed versioned migrations for future schema changes.
- **Implemented API/client:** every runner player entry has `runner: {status, endedAt?, caughtPosition?}`; hunter/direct-spectator entries omit `runner`. `status` is `active`, `caught`, or `finished`; `endedAt` is absent while active and present for either outcome. Only caught runners with a retained report have `caughtPosition`. Removed the top-level `caughtAt`, `finishedAt`, and `caughtPosition` fields without a legacy API compatibility layer. OpenAPI and the app client are regenerated; catch/finish UI, markers, and tracking checks use the new status. Game state also supports `status: ended`, game-level `endedAt`, viewer `role: player | spectator`, and original affiliation `team: runner | hunter | spectator`. The public result endpoint has its own coordinate-free schema, displayed by the shared result screen. Spectator locations are enforced server-side; direct-join app flow is implemented and timeline remains separate work.
- Verify persistence/reopening of the new schema, valid transitions, unchanged Ready/finish location checks and override, visibility, historical joker snapshots, retention, and deletion cascades with regression tests. Review each step before proceeding.

### Game result and history view [minimal API/UI done; full history planned]

- **Result entry [implemented]:** **"Spielergebnis ansehen"** on the start screen accepts a full **game ID** (not a runner or hunter join code). Leading/trailing whitespace and uppercase hex are normalized; malformed IDs are rejected without a request. Joining, authentication and location permission are not required. The same screen is directly addressable at `/results/{sessionId}` (installed-app scheme: `catch-me://results/{sessionId}`).
- The view is available **only for ended games**. The backend must enforce this, not just hide the screen: ongoing games must never expose result/history data through this lookup.
- **Minimal result API [implemented]:** `GET /api/games/{sessionId}/result` is accessible without authentication or joining, but only after the game ends. Knowing the full 32-character lowercase hexadecimal ID permits viewing player names/outcomes/times and hunter-team affiliation; the ID is not a player token or a six-digit join code. The response is `{sessionId, startsAt, endedAt, durationSeconds, playground, route, players, events}`. `playground` has the same shape as in the game state (center, bounds, rows, columns, cell size); `route` is the shared runner route with start and stop landmarks and distance, public once the game has ended (hunters never saw the stop during play). Duration is whole seconds from start to end, rounded down. Players stay in join order (ties by player ID), with `{playerId, name, team}`, plus `hunterTeam` for hunters who chose one, or `runner: {status, endedAt}` for runners (`caught` or `finished`, never a catch-position field), and `track` for runners and hunters (see Full history). `events` is the whole event timeline, oldest first, with the same coordinate-free event kinds as `GET /api/me/timeline`. Unknown and unfinished games both return the same `404`; malformed IDs return `400`; unsupported methods `405`. No cells, joker results, reveals, sketches, catch positions, join codes, player tokens or token hashes are returned. The result uses a separate domain projection and HTTP schema; loading it reads the used jokers (only kind, user and time reach the result) and the runners' and hunters' positions from start to end (see Full history), but never reveals or sketches. Games deleted after retention return the same `404` (see Retention). Responses use `Cache-Control: no-store` and are gzip-compressed when the client accepts it (`Accept-Encoding: gzip`, `Vary: Accept-Encoding`); other endpoints are not compressed. OpenAPI and the generated client include `getGameResult`. No winner, ranking, joker analysis or graphics are implemented.
- **Minimal result UI [implemented]:** display the selectable game ID, start/end timestamps, duration (minutes:seconds), runners with caught/finished timestamps and hunters with their hunter team, and a chronological "Timeline" card of all events, in German and English. There is no winner ranking yet; movement is shown as a replay (see Replay). Show loading, retryable network/backend errors, and one ambiguous message for `404` (unknown or unfinished game). A result for a different game ID is rejected, and a late request cannot replace a different game's result. The ID is a confidential access key, not a publicly listed identifier; the screen explains that anyone knowing it can view the result, and the app's development request log redacts result IDs. Backend/proxy access-log privacy remains part of production hardening.
- **Full history [implemented]:** the result includes every runner's and hunter's real track: their stored reports from the game's start to its end (inclusive), oldest first, each with coordinates, accuracy and server report time. Lobby/countdown reports are never included. Tracks are thinned on the server: a report is kept only if it is at least **5 seconds** after the previously kept one, and the player's last report in that window is always kept. **API:** each runner/hunter result entry has a required `track` array (possibly empty) of `{latitude, longitude, accuracyMeters, recordedAt}`; direct spectators omit `track`. The result screen plays the tracks back (see Replay). Runners and hunters always have a track (possibly empty); direct spectators report no positions and have none. Access uses the same full-game-ID rule without additional sign-in, only after the whole game ends. Joker effects (fake reveals, snapshots), reveals and sketches are not part of the tracks; adding joker effects to explain the match remains open. Visualization: see Replay below. Add `left` only with the running-game leave feature.
- **Track response limit [implemented]:** each result `track` contains at most **120,962 points**, enough for seven days at the normal 5-second cadence plus endpoint allowance. If the normally thinned track exceeds this limit, the server samples evenly across its indices while preserving the first and last reports. This does not impose a game time limit or delete stored position reports; it only bounds each result track. The OpenAPI `maxItems` documents the same enforced limit.
- **Automatic navigation [implemented]:** when a focused gameplay screen (including the joker modal) receives `ended`, stop location reporting and automatically replace the gameplay stack with this same result route. Restoring an ended session does the same. Clear the completed game's stored player token so returning to the start screen does not resume it again. A direct lookup does not join a game or overwrite an unrelated player's session. There is an explicit return-to-start button, also for direct links and errors. No background push navigation is promised: a background location report rejected with `409` stops background sharing; foreground state polling discovers the end and opens the result when the app is active again.
- **Reproducible development test data [completed-game generator and container wrapper implemented; broader coverage planned]:** standalone Go command `backend/cmd/devfixture`, requiring an existing initialized database and explicit `-confirm-development`, inserts a new completed synthetic game in one transaction without updating/deleting existing data or creating/migrating tables. It is not included in the server runtime image and has no HTTP endpoint. `bash scripts/seed-game.sh --confirm-development` builds/runs the separate Compose `devfixture` tool service against the backend's existing `game_data` volume as the same container user, without restarting/rebuilding backend or app; no local Go/SQLite installation is needed. The service belongs to the opt-in `tools` profile and can also be invoked directly with `docker compose run` (see README). The fixture has **4 runners, 16 hunters in 4 teams**, 4 hours of game time, a 6 × 6 grid with 1000 m cells, 30-minute reveals, and reports every 5 seconds (**54,740 position rows**). Two runners are caught at 1:45 h/2:45 h; two finish at 3:30 h/4:00 h at the shared destination. Reports stop at runner retirement or game end. Synthetic routes include pauses, detours and nearby hunter teammates; names/landmarks are marked `TEST`, and coordinates are invented, not real player recordings or street-network routing. All six implemented joker kinds are used (18 uses), with four team sketches and one recorded route regeneration. The command prints the full game ID; end time is five minutes before invocation to leave the normal retention window. Tests cover result/gameplay loading, track cadence/bounds/outcome endpoints, timeline joker coverage, repeated insertion without replacement, transaction rollback and retention. This ended-game fixture does not test live permissions or simulate live GPS. **Later:** direct spectators and running-game permission tests, plus leaving/zone alerts/traps when those features exist. Reveals remain derived from position history, not separate seed rows; no planned feature is presented as implemented.
- **Spectator coverage [planned]:** extend fixtures/tests with spectators who joined from the beginning, caught/finished runners converted to spectators, and their event timeline. Verify unrestricted spectator locations versus restricted active-player responses, no spectator position reporting or gameplay actions, and unchanged runner outcomes/end-condition evaluation after conversion. Live-view permission checks also need running-game test cases; an ended-game fixture alone cannot prove them.
- **Replay [app implemented; not device-tested]:** the result screen shows the tracks only as a dynamic replay, no static overview: a map with the playground grid, start and stop landmarks (pins), and every runner and hunter as a small dot centered on their position (first letter of the name inside), in their team color with a tail of the last 30 minutes of game time. Runners are blue; each hunter team gets its own color (red, orange, purple, teal, brown, pink in join order of the team's first member, repeating after six teams). A legend below the map lists the runners and every hunter team with its color. Positions between two track points are interpolated linearly; before a player's first point they are hidden, after their last point (catch, finish or last report) they stay at that point. Controls: play/pause (restarting from the beginning at the end), a draggable time scrubber from start to end with elapsed and total game time, and speeds 10×, 60× (default) and 300×. The replay advances in 100 ms steps. Following a player, filtering teams/players and jumping to timeline events are later extensions.
- **Fullscreen replay [app implemented; not device-tested]:** the replay uses the existing map expand/close controls. Fullscreen shows the same animated map, team legend, time scrubber, play/pause and speed controls. One shared replay clock preserves time, speed and playing state across opening/closing, without another result request. Controls sit below the map with bottom/side safe-area insets; their panel scrolls and takes at most half the screen when space is limited. The inline native map is unmounted while fullscreen is open, avoiding a second animated map behind the modal; returning fits the inline map to the playground again, as with existing fullscreen maps.
- **Retention [implemented]:** whole games are deleted with all their players, runner states, positions, jokers, sketches and zone alerts **7 days after their end**; games that never ended (abandoned lobbies, never-finished games) 7 days after their start, or creation if they never started. The cleanup runs at server startup and then hourly, so a game can stay reachable up to about an hour longer. Afterwards the result returns the same `404` as for unknown games. Each cleanup also deletes orphaned rows whose game or player no longer exists. Leaving still deletes a player's positions immediately. **Open:** whether leaving should retain history until the game is deleted.

### Jokers [existing kinds implemented; new kinds and configurable allowances planned]

One-off special abilities on top of the periodic reveals. A joker belongs to a team (runners, or one hunter team), except **fake position**, which belongs to each runner individually. The app has a joker sheet (the "Jokers" button on the game screen) listing the player's personal and team jokers.

**Show runners** (hunter teams) [implemented]: once per game and hunter team, while the game is running, any hunter of the team can use it. The team then sees where every runner was at that moment (each runner's last report at or before the use). The result stays on the map, in a different color than the reveals, and is visible only to that hunter team; other hunter teams still have their own joker. **Runners are told [implemented; not device-tested]:** every runner sees which hunter team used it and when, but never what it showed. The runner game state has a required `locatedBy` list (oldest first) of `{at, hunterTeam}` with every use made while that runner was active, so a use at or after their catch/finish is left out. This is derived from the stored joker uses; nothing extra is stored. It is always on, with no creation setting. **App:** runners' joker sheet has a "Location queried" card listing every use (time and hunter team). The game screen's top card shows the newest use for 5 minutes, next to the newest zone alert. Every use triggers a local notification ("Location queried", body with time and hunter team), using the same mechanism as zone alerts (see Zone alert). The hunters' joker text says that runners are told. The server stores only that the team used it (and when); the positions are derived from the stored position history, like reveals. Using it again is a `409`.

With the default allowance of 1, every joker can be used once per game and team, except **fake position**, which can be used once per game **per runner**. The server enforces the configured per-kind allowance (0–5), not a fixed one-use limit, and every use keeps its own result (see Configurable allowances). Jokers can only be used while the game is running; using a disabled or exhausted joker is a `409`. The per-kind descriptions below describe one use; with a larger allowance, each further use works the same way and adds its own result.

**Configurable allowances [implemented; app not device-tested]:** per-kind **0–5** allowances are chosen at game creation, default **1** for every kind. Preserve ownership: shared runner jokers spend the runner team's allowance, hunter jokers spend the respective hunter team's allowance, and personal jokers spend the individual runner's allowance.

- **Implemented foundation:** `game.JokerSettings` has a fixed, typed field per implemented kind, a parsed `JokerAllowance` (0–5, read with `Max()`), and separate `TrapSettings` that can later gain kind-specific fields. The kind-to-field mapping exists once in the domain. Settings are stored as embedded columns on the game; existing games receive 1 per kind, and explicitly stored 0 remains 0. The creation service stores the supplied settings without defaulting them. Settings are fixed at creation, not modified by lobby actions.
- **Domain rules implemented:** `UseJoker` rejects disabled/exhausted kinds and counts all uses in the correct ownership scope. `JokersFor` returns the full permitted per-kind history without overwriting earlier results, and `available` (running game, active player, allowance not used up). It does not check joker-specific prerequisites such as the compass position or a pending reveal joker; those are rejected on use. Pending reveal jokers still block only that runner's next reveal joker; rejected actions never spend uses. Multiple traps of one hunter team can coexist and trigger independently; repeated fake positions affect their individual next reveals without changing stored real positions.
- **Multi-use persistence implemented:** the schema uses a non-unique `joker_scope` index on `(game_id, team, kind)` instead of the former `joker_once` constraint. Each accepted use remains its own append-only row; loading reconstructs each result independently from its own time/target and position history, including independent trap triggers and reveal-joker effects. The existing serialized load/change/save transaction enforces allowances without relying on database uniqueness. **Development schema note:** AutoMigrate will not remove an old `joker_once` index; explicitly remove that index from an older development database before testing multiple uses (see README). No automatic compatibility migration or data reset is provided.
- **Creation API implemented:** `POST /api/games` requires a non-null `jokers` object, with a non-null settings object for each of `showRunners`, `queryZone`, `compass`, `trap`, `zoneOnly`, `fakePosition`, and `showHunters`. Every object requires integer `allowance` 0–5; missing/null objects or allowances, invalid types/ranges and unknown fields are rejected with `400`. The server supplies no defaults or compatibility fallback. Requests and responses share one schema (`ControllerJokerSettings`). The app sends the allowances chosen on the create screen (default 1 per kind), always explicitly for every kind.
- **Configuration UI implemented:** the create screen's "Jokers" card offers 0–5 per kind as selectable buttons, grouped into hunter jokers (per hunter team) and runner jokers (shared; fake position per runner), and is hidden once the game is created. The client rejects invalid allowances before sending, like the other settings.
- **State API implemented:** the creation response's `game` and every authenticated game-state variant include required `jokerSettings`, with the same per-kind `{allowance}` objects as the creation request's `jokers`. This is immutable configuration, not another team's usage history, and is also visible to direct/converted spectators. Every permitted personal/team joker has `kind`, `available` and a required `uses` list (at most 5, oldest first, empty while unused). Each use has `usedAt` and that kind's result: `positions` (showRunners/showHunters), `cell`/`found` (queryZone), `origin`/`bearings` (compass), `point`/`activeAt`/optional `triggeredAt` (trap), `point` (fakePosition); runner uses also have `usedBy`. Shared jokers list every use of the owning team; fakePosition lists only the requesting runner's own uses. There is no separate remaining count: remaining uses are `jokerSettings[kind].allowance` minus `uses.length`. Direct spectators still have `jokers: []`.
- **App implemented:** the joker sheet shows per kind "n of m uses left" (or "not enabled" for 0), every use with its time, user and result, and the use button while `available`. The map draws the results of every use: each showRunners/showHunters snapshot, every queried zone (also the same cell twice), every compass origin with its arrows, every fake-position point, and every trap circle with its own status. Joker texts no longer promise a single use.
- Configurable trap radius/activation delay are not part of these steps; their current constants stay 100 m/20 minutes. The automatic zone alert has no allowance, only an on/off switch (see Zone alert).

Caught runners cannot use any joker. Hunter location jokers used at or after a runner's catch exclude that runner; earlier snapshots keep their historical result when reloaded.

**Query a zone** (hunter teams) [implemented]: any hunter of the team picks one cell of the game's grid (in the app: a cell picker in the joker sheet; a cell outside the grid is a `400`). The team gets a yes/no answer: was at least one runner inside that cell at that moment (each runner's last report at or before the use; a runner without a report counts as outside)? The answer does not say how many runners or which. The cell and the answer stay on the team's map; only that hunter team sees them, and runners are not told. The server stores the cell and the time; the answer is derived from the position history.

**Compass** (hunter teams) [implemented]: any hunter of the team can use it, but only after reporting a position (otherwise a `409`, and the joker stays available). The team learns in which **direction** every runner was at that moment, seen from that hunter's last reported position at the use (the **origin**): for each runner, the bearing from the origin to the runner's last report at or before the use, in whole degrees clockwise from true north (0–359). A runner without a report is left out. The server never sends the runners' positions or distances, and the bearings carry no player IDs; they are sorted by angle, so they do not reveal which runner is which. The app draws one arrow of fixed length (one cell width) per bearing, starting at the origin, without names. The result stays on the team's map; only that hunter team sees it, and runners are not told. The server stores the origin and the time; the bearings are derived from the position history, like reveals.

**Runner jokers:** show hunters and show only the zone belong to the runner team as a whole: each exists once per game, and when one runner uses it, it is used up for all runners. All runners see which shared runner jokers were used, by whom and when. **Fake position is personal:** each runner has their own use, status, and chosen point; using it does not spend another runner's joker. The joker sheet and fake-position marker show only the requesting runner's own use. Hunters are never told that a joker was used. The reveal jokers (show only the zone, fake position) affect only the runner who used it, and only that runner's **next reveal**; hunters only see their effect at the reveal. A runner can have at most one pending reveal joker at a time (a second one before the next reveal is a `409`). Different runners can each have a fake-position joker pending at the same time.

- **Show hunters** [implemented]: any runner can use it. All runners then see where every hunter (of every hunter team) was at that moment (each hunter's last report at or before the use; a hunter without a report is left out). It is a snapshot, not live: the result stays on the runners' map in its own color. Hunters are not told. It acts immediately and does not touch any reveal, so the pending-joker rule does not apply: it neither blocks nor is blocked by a pending reveal joker. The server stores who used it and when; the positions are derived from the stored position history, like reveals.

- **Show only the zone** [implemented]: at the next reveal (the first reveal time strictly after the use), hunters see only the cell this runner is in **at that reveal** (their last report before it, like every reveal), not the exact position; the app highlights the cell on the map with the reveal's numbered marker in its middle. If the runner is outside the playground then, the reveal has neither cell nor position (no marker, but the numbering keeps the gap). The server stores who used it and when; the zone is derived like reveals, and the position of that reveal is never sent to hunters. Runners see the joker in their joker sheet, and once used, who used it and when.
- **Fake position** [implemented]: once per game per runner, the runner picks any point inside the playground (in the app by moving a map until a crosshair is on it; a point outside is a `400`). At the next reveal (the first reveal time strictly after the use), hunters see that point instead of the real position, looking like a normal reveal: it keeps the accuracy and report time of the real position, only the coordinates are replaced. If the runner has no report before that reveal, there is no reveal, as usual. The server stores who used it, when, and the point; the runner sees their own point as a marker on their map. The server never sends the real position of that reveal to hunters (before the game has ended); the faked reveal stays faked. Existing stored uses remain spent for the runner who used them; other runners retain their personal use.

- **Zone alert** (runners, passive and personal) [implemented, including local notifications; not device-tested]: switched on or off per game at creation (`zoneAlert: {enabled}`, default on). It has no 0–5 allowance and is never used actively. While the game is running, an active runner is alerted the **first time each individual hunter** is in the runner's grid cell: at most **once per game per runner and hunter**, so a runner gets at most as many alerts as the game has hunters. A later re-entry of the same hunter never alerts again, but another hunter (also of the same hunter team) does, and each runner has their own alert state. Evaluated on every real position report from either side, by server time: the new report and the opponent's latest report must lie in the same cell, and the opponent's report must be at most **60 s** old. Reports outside the playground never alert; fake positions do not count, since they never change stored real positions. An alert is stored when it is raised (not derived), so it can be notified exactly once (table `zone_alerts`, append-only, unique per game, runner and hunter, deleted with its game). It tells the runner the **hunter, hunter team, cell and time**, never coordinates: the runner game state has a required `zoneAlerts` list (oldest first, empty without alerts) of `{at, hunterId, cell}`; the hunter's name and team come from the state's `players`. Only the alerted runner sees their own alerts (also after their catch/finish); other runners and hunters are not told. The spectator timeline and the result list it as a `zoneAlert` event with `runner`, `hunter` (each `{playerId, name}`), `hunterTeam` and `at`, without the cell. The creation request requires `jokers.zoneAlert: {enabled: boolean}` (missing/null is a `400`); `jokerSettings` returns it. **App (implemented):** the create screen's joker card has an on/off choice (default on). Runners' joker sheet has a "Zone alert" card that says whether it is on and lists their own alerts (time, hunter, hunter team, cell). While playing, the game screen's top card shows the newest alert for 5 minutes by server time. **Notifications (implemented; not device-tested):** the runner's app shows a **local notification** (title "Zone alert", body with time, hunter, hunter team and cell, no payload data) for every alert at most 5 minutes old that it has not notified in the current app run. It checks every game state the game screen receives and every response to a background position report, so it also works with the screen off while background sharing runs. Each alert has a fixed notification identifier (game and hunter), so a repeat after an app restart replaces the earlier notification instead of adding one. When an active runner opens the game screen, the app asks for the notification permission once (also needed for the always-on showRunners notice). Android uses a "Hunter warnings" channel with high importance. If notifications are denied, the top card says so and alerts stay visible in the app only. Push delivery while the app neither polls nor reports stays open.
- **Trap** (hunter teams) [implemented; app not device-tested]: once per game and hunter team, while the game is running, any hunter of the team picks a point **inside the playground** (outside is a `400`) to place a trap: `{kind: "trap", latitude, longitude}`; in the app with the same crosshair map as fake position. The trap becomes active **20 minutes after placement**, measured by server time; before then it cannot trigger. It triggers **once**, at the first runner report recorded at or after the activation within **100 m** of its point; earlier reports never count, even if still the runner's latest, and hunter reports never trigger. Runners only report while active, so only active runners trigger it. Like reveals, the trigger is derived from the stored position history when the game is loaded, not stored; the server stores only the team, the time and the point. Only the placing hunter team sees the trap: its `point`, `usedAt`, `activeAt` and, once triggered, `triggeredAt` (the time of the triggering report), but **not which runner** triggered it nor that runner's position. Other hunter teams and runners are not told; runners get no notification. The team's map shows the trap as a 100 m circle (not a pin): grey while waiting, orange while active, red once triggered; the joker sheet shows the same status as of the last game state. The timeline shows the placement as a hunter joker use and a `trapTriggered` event with the hunter team and time, without runner or coordinates. Spectators see no trap overlays. Trap timing follows lazy evaluation.

### Hunter team sketches [done: MVP]

- Hunters of one hunter team draw freehand lines (**sketches**) on the map that only their team sees. Runners and other hunter teams never receive them; the server filters them like positions.
- Drawing is possible **only while the game is running**, for hunters in a hunter team, on the game screen's map ("Draw" button; the map stops moving while drawing). A line is sent when the finger is lifted; teammates see it with the next game state poll (no live drawing). The app thins longer lines to 500 points.
- A sketch is a list of 2–500 points (latitude ±80°, longitude ±180°), in one color in the MVP. A hunter team has at most 200 sketches.
- **Any team member can clear all** of the team's sketches at once. There is no undo or deleting single lines in the MVP.
- Sketches belong to the hunter team, not to the drawing player: they stay when a player leaves. (Leaving is not possible while running, and hunter teams only change before the start, so a team cannot disappear while it has sketches.)
- Sketches are kept for the later replay and deleted with their whole game (see Retention under "Game result and history view").
- Later: colors, undo, deleting single lines, notes or markers, sketches for runners.

## API (milestones 1 to 3)

**Compatibility:** the game is not live yet, so breaking API changes are allowed; the app and the backend are always changed and shipped together (the generated client comes from the same commit). There is no API versioning: paths are unversioned (`/api/...`), there is no version header, and the OpenAPI document's version stays at `0.1.0`. Before the first release, decide on a versioning and compatibility policy (installed apps then lag behind the backend).

| Method and path | Auth | Purpose |
|---|---|---|
| `POST /api/games` | – | Create a game `{latitude, longitude, cellSizeMeters, gridSize, revealIntervalMinutes, jokers}` (all fields required and non-null; `jokers` requires a settings object with integer `allowance` 0–5 for every implemented kind, plus `zoneAlert: {enabled}`; defaults are selected by the app, not supplied by the backend). Optional `route: {start, stop}` with coordinates chooses the route instead of generating it (see Route); omitted or `null` generates it. Returns the game (with `revealIntervalMinutes` and `jokerSettings`) and runner/hunter/spectator join codes. |
| `GET /api/games/{sessionId}/result` | - | Public result for an ended game: times, duration, player names/teams, runner outcomes and the event timeline; no credentials or coordinates. Unknown/unfinished games return `404`. |
| `POST /api/players` | – | Join with `{code, name}`. Returns the player token and the game state. |
| `GET /api/me/game` | Bearer | Game state as seen by the requesting player. |
| `GET /api/me/timeline` | Bearer | Event timeline for spectators (`409` for active players). |
| `POST /api/me/caught` | Bearer | Permanently mark the requesting runner caught, while running, with no request body or proximity check. Idempotent: retries preserve the original catch. Returns the game state. `409` for hunters, finished runners, or before the game is running. |
| `POST /api/me/finish` | Bearer | Permanently finish the authenticated runner, while running; no request body. Shares the Ready position check (50 m, 30 s) against the stop, and the same development override. Returns game state with `runner.status: finished` and `runner.endedAt`, never finish coordinates. Idempotent retries preserve the original time. `409` for hunters, caught runners, pre-running games, or failed position checks. |
| `PUT /api/me/ready` | Bearer | Set `{ready: true/false}`. Returns the game state. |
| `POST /api/me/route` | Bearer | Regenerate the game's route (runners, see Route). Returns the game state. |
| `PUT /api/me/hunter-team` | Bearer | Join or create the hunter team `{name}` (hunters, not ready, before the start). Returns the game state. |
| `PUT /api/me/position` | Bearer | Report `{latitude, longitude, accuracyMeters}`. Returns the game state. Caught or finished runners receive `409`; no report is stored. |
| `POST /api/me/jokers` | Bearer | Use a personal or team joker: hunters in a hunter team `{kind: "showRunners"}`, `{kind: "queryZone", cell: "C4"}`, `{kind: "compass"}`, or `{kind: "trap", latitude, longitude}`, runners `{kind: "zoneOnly"}`, `{kind: "fakePosition", latitude, longitude}`, or `{kind: "showHunters"}` (exactly the fields of that joker, anything else is a `400`; while running, uses spend the configured allowance: fakePosition per runner, other jokers per owning team; a runner whose last reveal joker has not acted yet must wait for their next reveal before using another reveal joker). Returns the game state with every use of that joker kind. |
| `POST /api/me/sketches` | Bearer | Add a sketch `{points: [{latitude, longitude}, …]}` for the player's hunter team (while running; body up to 64 KiB, other endpoints 1024 bytes). Returns the game state. |
| `DELETE /api/me/sketches` | Bearer | Clear all sketches of the player's hunter team (while running). Returns the game state. |
| `DELETE /api/me` | Bearer | Leave the game (lobby and countdown only). |

The game state contains status, server time, scheduled start/end times where present, next reveal time while running, playground, required immutable `jokerSettings`, the requesting participant's ID, original `team` and viewing `role`, all available join codes, and the participant list. Runner variants additionally include the route, `routeRegenerationsLeft`, their own `zoneAlerts` and the showRunners uses that included them (`locatedBy`); hunter variants include their team's `sketches`. The direct-spectator variant includes the same required `route` as runners, no sketches/regeneration counter and `jokers: []`. Active players receive their permitted team/personal `jokers`, each picked by `kind` with `available` and a `uses` list (oldest first) holding each use's `usedAt` and that kind's result fields; remaining uses are `jokerSettings[kind].allowance` minus `uses.length`. Active-player locations remain restricted: own position, hunter teammates always, runner teammates while running; hunters see runner `reveals` (`position`, `zone` or `outside`) instead of live runner reports. Spectator viewers receive all latest real reports only while running, without periodic reveals, with frozen catch/finish reports as described under Spectators. Direct spectators themselves have no location or runner outcome. Clients compute countdowns from server time rather than the phone's absolute clock.

Each runner player entry includes `runner.status` (`active`, `caught`, `finished`). `runner.endedAt` is the server-recorded outcome time, absent while active; `runner.caughtPosition` exists only for a caught runner with a retained report. Hunters have no `runner` object. Completed runners have no ordinary position or reveals. The former top-level `caughtAt`, `finishedAt`, and `caughtPosition` fields are removed; the app and backend must use the matching contract.

Errors: `400` invalid input, `401` missing or unknown token, `404` unknown game or join code, `409` rule violation (game started, full, name taken, route regeneration not allowed (including a chosen route) or no other route available, hunter team change not allowed, runner not at the start, hunter without a team, joker not available: game not running, disabled/exhausted allowance, not a joker of the player's team, a hunter without a team, or the runner's last reveal joker has not acted yet; a compass before the hunter reported a position; sketch not allowed: game not running, not a hunter in a team, or the team's sketch limit reached).

### Planned API extensions (not implemented)

- Leaving a running game; automatic end for caught/finished runners, game ID/end time, and app-side result navigation are implemented.
- Broader statistics/historical graphics; the minimal game-ID result API/UI is implemented, without coordinates or history yet. Future full-coordinate history uses the agreed confidential-game-ID access rule after game end; define response details and retention handling before implementation.
- Creation settings UI for each joker kind's 0–5 allowance, the zone-alert API, its creation switch, the runner's alert display and local notifications are implemented. State API settings and per-kind use lists, and their display in the app, are implemented.
- Notification device registration/delivery as required by the chosen notification design. Keep all generated API outputs unchanged until the corresponding backend implementation is requested.
